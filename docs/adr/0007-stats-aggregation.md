# ADR-0007: 통계 집계 — 네이티브 SQL 집계 + 전환율만 애플리케이션 계산

## 상태
채택

## 배경
캠페인/채널 통계는 방문·방문자(DISTINCT)·신청을 집계한다. 이를 엔티티를 메모리로
읽어와 스트림으로 세면 데이터가 늘수록 느리고, 전환율까지 SQL에 넣으면 0 나누기와
반올림 규칙이 DB 방언에 흩어진다. 또 데이터가 없는 채널을 어떻게 표시할지 결정해야 한다.

## 결정
- 방문/방문자/신청 **집계는 네이티브 SQL**로 DB에서 수행한다
  (`VisitRepository`/`LeadRepository`의 `campaign_id` 조인 + `COUNT`, `COUNT(DISTINCT ...)`).
- **전환율만 애플리케이션(`StatsService.conversionRate`)에서 계산**한다:
  `visitors == 0 ? 0.0 : round(submissions/visitors*100, 소수1자리)`.
- 채널별 통계는 **`Channel` enum 4종을 항상 모두 반환**한다. SQL은 데이터가 있는
  채널만 그룹으로 돌려주므로, 서비스가 없는 채널을 0으로 채운다.

## 근거
- 집계를 DB에 맡기면 전체 로우를 앱으로 옮기지 않아 빠르고 메모리를 아낀다.
- 0 나누기 방어와 반올림은 한 곳(애플리케이션)에 두어야 정의가 일관되고 테스트가 쉽다.
  DB 방언에 로직을 분산시키지 않는다.
- 4종 고정 반환은 화면·API 소비자가 "인스타는 왜 없지?"를 고민하지 않게 한다.
  성과가 0인 채널도 명시적으로 0.0%로 보여야 채널 간 비교가 완전해진다.

## 한계 / 후속
- 네이티브 SQL은 PostgreSQL에 결합된다. DB를 바꾸면 쿼리를 손봐야 하나, 과제 스택은
  PostgreSQL 16으로 고정이다.
- 통계는 요청 시점 집계(온디맨드)다. 트래픽이 커지면 집계 캐시/사전 계산이 필요하나
  현 규모에는 과설계다.
