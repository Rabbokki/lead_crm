# ADR-0004: 폼 필드 스키마 — JSONB 저장 + jsoup 자동 추출

## 상태
채택

## 배경
폼마다 입력 필드가 다르다(이름·이메일만 받는 폼, 연락처·관심분야까지 받는 폼 등).
필드를 관계형으로 정규화(예: `form_fields` 테이블, `lead_values` 테이블)하면
스키마가 복잡해지고 조회마다 조인이 늘어난다. 반면 과제 범위에는 "드래그앤드롭
범용 폼 빌더"가 **명시적으로 제외**되어 있어, 필드 편집 UI를 따로 만들 수도 없다.

## 결정
- 폼의 필드 정의 `forms.field_schema`를 **JSONB**로 저장한다
  (`@JdbcTypeCode(SqlTypes.JSON)`, 별도 라이브러리 불필요).
- 필드는 UI로 편집하지 않고, 등록된 **템플릿 HTML을 jsoup으로 파싱**해
  `name` 속성을 가진 `input`/`textarea`/`select`를 `FieldDef(name, type, required)`로
  자동 추출한다(`FormService.extractFields`). 문서 순서 유지, `name` 중복은 첫 번째만 사용.
- 제출 시 이 `field_schema`를 **화이트리스트**로 삼아 정의된 필드만 `leads.payload`에
  저장한다(정의 외 필드 무시). `required` 필드가 비면 422로 거부한다.
- 신청 데이터 `leads.payload`도 폼마다 형태가 달라 **JSONB**로 저장한다.

## 근거
- 필드 구성이 폼마다 가변적이라 문서형(JSONB)이 정규화보다 단순하고 조회가 빠르다.
- 템플릿 HTML이 곧 필드의 원천이므로, HTML에서 필드를 추출하면 폼 빌더 없이도
  "실물과 스키마의 일치"가 자동 보장된다(제외 범위와도 정합).
- 화이트리스트 저장은 악성/불필요 파라미터가 payload에 섞이는 것을 막는다.

## 한계 / 후속
- JSONB는 컬럼 단위 제약(길이·형식)을 DB가 강제하지 못한다. 값 검증은 애플리케이션
  책임이며 현재는 required 여부만 검사한다. 형식 검증(이메일 패턴 등)은 후속 과제.
- 필드 타입은 HTML의 `type` 속성을 그대로 따르므로, 템플릿 작성 품질에 의존한다.
